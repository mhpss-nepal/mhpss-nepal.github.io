Access and enforcement status

The pages in this branch show a proposed client workflow. They do not prove who the server allows to read, write, publish, delete or administer.

Server enforcement is unverified. The authoritative Firestore Rules are not versioned in this monorepo, and the real role-document key scheme has not been established here. No deployment or access claim may rely on these client controls. See infra/README.md in the source.

CLIENT INTENTWhat the interface is designed to do

  • Save form records locally first and queue a network write when configured.
  • Strip focal-point contact fields in the client before a queued record is sent.
  • Prompt for sign-in before client paths that request full register reads.
  • Use a returned role document to show or hide client controls for reading, publishing and administration.
  • Preview public aggregate documents before the client attempts to publish them.

NOT ESTABLISHEDWhat this branch cannot claim

  • That unauthenticated or authenticated reads are allowed or denied as the client expects.
  • That any named client role has a particular server-enforced capability.
  • That role documents are keyed by email, UID or any other identifier.
  • That forbidden identity fields, document limits or publication constraints are enforced by the server.
  • That client-side hiding, validation or field stripping is an authorization or data-protection boundary.

DEPLOYMENT GATEEvidence required before use

The institution-owned Rules must be exported without copying production data, reviewed for least privilege, emulator-tested with allow and deny cases, coordinated with the institutional owner, and versioned through the normal review process. Until then this branch must not be deployed.

Draft client workflow only. Server enforcement is unverified.
